# 压缩之后，那条指令变成了历史

2026 年 11 月 16 日，OpenClaw 发布 v2026.11.5-beta.3。它的版本亮点只有两句话：降低 transcript 索引、裁剪与压缩过程中的内存压力；hydration 只流式传输被选中的 payload，并遵循一个可配置的摘要上限。同一天，同一个项目的 issue 列表里躺着三条同一主题的报告：大会话读取 context 时全量扫描 transcript，一次快照读要 19 到 25 秒（#185111）；约 864 MiB 的语料 memory index 报出 worker task capacity reached，而且不重试（#196505）；大型会话反复杀死 512 MB 的 SQLite worker，错误名是 ERR_WORKER_OUT_OF_MEMORY（#191847）。

一个版本在修的东西，和三条 issue 在痛的东西，是同一件事：当会话长到一定程度，上下文不再是一段文本，而是一份需要被索引、被裁剪、被压缩、被流式投递的状态库。它有三个无法回避的伴生成本——钱、时间、语义。这三笔账在 11 月 16 日这一天，被至少七个项目同时摊在了桌面上。

先看另外几个现场。OpenAI Codex 的 #27731 记录了一件比崩溃更麻烦的事：compact 之后恢复会话，模型把一段陈旧的用户 prompt 当成了当前指令执行。Qwen Code 在同一天的 PR #15936 里给压缩加了一条硬约束：压缩请求必须为摘要预留至少 4096 个输出 token，否则降级或拒绝。GitHub Copilot CLI 的 #2068 说，后台压缩会多消耗 1 次 premium request。OpenCode 的 #61020 则是模型目录里丢了上下文窗口的信息，于是压缩在错误的时点提前发生。

这些报告没有一条在讨论模型能力。它们讨论的都是记账方式：谁来付压缩的钱，压缩要花多久，压完之后哪句话还算“现在”。

## 第一本账：同一段前缀，付了两次钱

OpenClaw 的 #143017 是一份少见的成本取证。报告者用生产流量的 wire capture 反复补充证据，结论是 prompt 前缀被五种不同的路径重写，实测浪费了 21.3M 个 cache-write token。前一天的日报里还记着两件事：同一族问题的 #182891 报告每次请求的缓存 read 从 N 跌到 0；#130257 记录了子代理花费无法归因，父 turn 花了 0.04 美元，子代理花了 14.14 美元，相差约 350 倍。

把这三条放在一起，能看清 prompt cache 的成本结构。缓存按前缀匹配，前缀一旦变化，后面全部作废，下一次请求要把整段上下文重新写进缓存。缓存写入的价格通常高于命中读取，所以“前缀被重写五次”的代价，是同一段内容以更贵的单价被重新买了一遍，远不止五份钱。21.3M 个 cache-write token 是这件事的计量单位。

前缀为什么会漂移，日报没有列出那五种路径的具体内容。但从同批材料里可以推出几类常见成因：系统提示词里嵌入了每次都变的东西，比如时间戳、会话标识、顺序不稳定的记忆段；工具 Schema 的字段顺序或描述文本不稳定；上下文裁剪之后，前缀与上一轮的边界对不上；多后端切换时模板结构不同；摘要的注入位置发生变化。这几类的共同点是，每一次看起来都是合理的动态生成，没有一处像错误。工程上唯一有效的约束是把它当接口来管：前缀的字节序列要么稳定，要么显式版本化，中间状态最贵。

真正的麻烦在于，这种浪费不会以错误的形式出现。请求成功，回答正常，只有账单在涨。使用者看到的是“这个月怎么贵了”，看不到“某一行系统提示词被重新排序了”。这类缺陷的观测面在计费侧，不在功能侧，所以它天然容易被漏掉。

同一天的成本账还有几笔性质不同的。

Copilot CLI 的 #2068（5 个赞）指向后台压缩本身计费：一次压缩消耗一次 premium request。压缩本来是省钱的机制，在这里变成了一次独立的收费动作。Codex 的 #54227 是另一种形态：一位每月付 200 美元的用户，连续一个多月遭遇 server_overloaded 和远程 compact 失败。付费额度与可用性脱钩，账单照付，任务不完成。

OpenCode 的 #59387 攒到了 370 条评论，主题是免费层的额度问题——“额度已用尽”“重置从不发生”。配套的 #52894 只要求一件事：把重置时间精确显示出来。这条请求之所以有 13 条评论，是因为在缺少重置时间的情况下，用户无法区分“我用完了”和“系统算错了”。

还有一类成本藏在扩展层。anthropics/skills 的 #1487 指出，claude-api 这个 Skill 单次注入约 156k token，直接把上下文打爆。Gemini CLI 的 #19561 记录单轮基线约 36.6k token，而 #24246 说工具数超过 128 个就会触发 400 错误。工具定义也是上下文，Schema 也是 token，装得越多，每一轮都要重付一次。

把这些现场并排放，能看到成本并不是“单价乘以 token 数”这么简单的一个乘积：

| 现场 | 工具 | 观测到的数字 | 成本落在哪一层 | 使用者能看到的信号 |
|---|---|---|---|---|
| #143017 前缀被五种方式重写 | OpenClaw | 21.3M cache-write token | 缓存写入层 | 只有账单，没有报错 |
| #130257 子代理花费不可归因 | OpenClaw | 父 0.04 美元 / 子 14.14 美元 | 记账粒度层 | 总额异常，无法定位 |
| #2068 后台压缩计费 | Copilot CLI | 每次压缩 1 次 premium request | 计费动作层 | 配额消耗快于预期 |
| #15936 摘要输出预算 | Qwen Code | 至少预留 4096 输出 token | 生成预算层 | 压缩被降级或拒绝 |
| #1487 Skill 注入体积 | Claude Code Skills | 单次约 156k token | 扩展注入层 | 上下文突然不够用 |
| #24246 工具数上限 | Gemini CLI | 超过 128 个工具报 400 | 协议负载层 | 请求直接失败 |

这张表里最值得记住的一行是第二行。前缀重写是浪费，但浪费可以度量；归因缺失是另一种问题——花费发生了，却无法指认是谁花的。当一个父任务只花了 4 美分、它调起的子代理花了 14 美元时，任何按父任务做预算的机制都会失效。成本治理的第一步不是省钱，是让每一笔钱都能落到一个可命名的对象上。

## 第二本账：19 秒的快照与一句过期的指令

钱的问题再贵，至少是可逆的。第二本账不是。

#185111 描述的是读取：大会话下，取一次 context 要把 transcript 全量扫一遍，耗时 19 到 25 秒。这个数字之所以重要，是因为它出现在“读”这一步，而不是“想”这一步。用户感知到的卡顿、超时、重试，很多时候不在模型推理，而在把状态从磁盘搬到内存的这段路上。beta.3 的 hydration 改动直接对着它：只流式传输被选中的 payload，不再整份搬运。

#196505 的 864 MiB 索引与 worker task capacity reached 说明另一件事：索引本身成了有容量上限的资源，触顶之后不重试。一个不重试的容量错误，在日志里只出现一次，然后表现为“这个会话的记忆好像不全”。#191847 里那个 512 MB 的 SQLite worker 被反复杀死，则是同一个瓶颈的暴力版本——进程被杀，正在处理的轮次一起消失。

Codex 的 #61568 把这个问题推到了启动阶段：0.167 之后，TUI 启动时会加载其他线程的完整 rollout，单次启动占用数 GB 内存，而 0.166 是正常的。这条已经被关闭，但它留下的形状很典型：一个为了“让用户看到全部历史”的便利设计，把启动成本变成了随会话数量线性增长的固定开销。

真正让第二本账变成正确性问题的是 #27731。compact 会丢弃原文、保留摘要；恢复时，摘要和后续消息拼回一个新的上下文。如果拼接顺序、角色标记或时间信息有任何一处不对，模型就会把摘要里的旧要求当成新的指令。它不会报错，它会照做。这就是标题里那句话的来历：压缩之后，那条指令变成了历史，但模型读到的语气是现在时。

OpenCode 的 #61020 是同一族缺陷的另一种触发方式：模型目录里缺少上下文窗口大小，压缩器按错误的阈值判断“快满了”，于是提前压缩。上下文窗口是模型元数据，属于那种“缺了也能跑、但会算错”的字段。这条已修复关闭，配套的 PR #64133 加上了冷却后重试。

Qwen Code 的 #15225 更隐蔽：auto-memory 把一个自动记忆目录作为独立的 user 消息附在 tool result 后面。结果是模型开始输出空泛承诺，而不是继续调用工具。原因不难推：一段以 user 身份出现的新指令，会和当前任务的工具调用意图竞争注意力。记忆注入的位置，本身就是一个会影响行为的设计变量。

这四条放在一起，可以给“压缩”下一个更准确的定义：它不是把长文本变短，而是把“状态”重新编码成“叙述”。编码过程中会丢掉三样东西——出处、时间、以及哪些内容是证据哪些是要求。丢掉之后，模型仍然能读懂这段话，所以没有任何一层会报警。

工程上的应对，这一天已经出现了三个方向。

第一个方向是把摘要的预算显式化。Qwen Code 的 #15936 要求为摘要预留至少 4096 个输出 token，超长时自动恢复。这条约束的含义是：摘要不是免费的副产品，它要从输出预算里切一块出来，切不出来就应该降级而不是硬压。

第二个方向是把任务状态搬出上下文。Gemini CLI 的 #18836 与 #21000 提出用持久化文件的 CRUD 替代把任务清单写进对话窗口的做法，理由是后者会随上下文腐烂。任务清单本来就不该占用对话历史，它属于外部状态，读写都应该走文件。

第三个方向是压缩后重新注入“当前目标”。这一条没有单一 issue 对应，但从 #27731 的失效形态可以直接推出来：如果压缩后第一件事是重申当前目标、当前约束和“以下是历史摘要”的边界标记，那么陈旧指令被误读的概率会显著下降。代价是每次压缩多花几百个 token，收益是把一类静默错误变成可检出、可复现的错误。

| 工具 | 压缩相关现场 | 触发条件 | 观测到的数字或结果 | 失效发生在哪一层 |
|---|---|---|---|---|
| OpenClaw | #185111 快照读全量扫描 | 大会话 | 19 到 25 秒 | 读取路径 |
| OpenClaw | #196505 索引触顶 | 约 864 MiB 语料 | worker task capacity reached，不重试 | 索引容量 |
| Codex | #27731 恢复后执行陈旧指令 | compact 后恢复 | 陈旧 prompt 被当作当前指令 | 语义拼接 |
| Codex | #61568 启动加载全量 rollout | 0.167 之后 | 单次启动数 GB 内存 | 启动路径 |
| OpenCode | #61020 提前压缩 | 模型目录缺窗口大小 | 压缩在错误阈值触发 | 模型元数据 |
| Qwen Code | #15225 记忆注入干扰 | auto-memory 附加消息 | 模型输出空泛承诺，停止调用工具 | 注入位置 |
| Qwen Code | #15936 摘要预算 | 压缩请求 | 至少 4096 输出 token | 生成预算 |

表格里七行，只有一行的后果是“报错”。其余六行的后果都是“看起来正常”。这就是上下文工程和普通后端工程最大的差别：普通后端的资源不足会抛异常，上下文的资源不足会降级成一段读得通、但含义已经变了的话。

还有一条当天被关闭的 P0 值得单独记（#193962）：从 2026.10.10 起，SQLite header-probe 超时让 openclaw update 无法到达新版本，也就是说，修复本身没法通过升级通道送到受害者手里，日报把这类问题称作“修复够不着受害者”的更新死锁。它和压缩没有技术关系，但共享同一个结构：一条系统里最贵的路径，往往是那条把东西送到用户手里的通道。通道坏了，做对的事等于没做。
## 四种失败形态，三种取舍

把 11 月 16 日前后这些报告按后果分类，压缩会呈现出四种不同的失败。

第一种是容量失败，表现是读不动。19 到 25 秒的快照读、864 MiB 的索引触顶、512 MB worker 被 OOM 杀死，都属于这一类。它们的共同点是恶化平缓、没有断崖，只有在会话足够长、索引足够大之后才显现。beta.3 对 transcript 索引、裁剪与压缩做内存优化，正是对这类失败的正面回应。

第二种是时态失败，表现是历史被当成现在。#27731 是最干净的样本：compact 之后恢复，模型执行了一段陈旧 prompt。这类失败特别难查，因为输出本身是合理的，只是对应了一个已经过期的目标。用户看到的是“它怎么又去做那件事了”，日志里找不到任何异常。

第三种是出处失败，表现是分不清哪段话从哪来。11 月 16 日 HN 上还有一条同型的样本：检测工具把一个 2020 年前写成的人类长文判定为 100% AI 生成。判断本身并不离谱，错的是把来源放错了位置——把人的文字归给了机器。Qwen Code 的 #17318 提出了一个系统性方案：对 shell 与远程工具的输出建立统一的“不可信上下文”标记，用来防御 prompt injection。这条建议的价值超出安全范畴——它实际上是在给上下文加来源标签。同一族的还有 OpenClaw 的 #127195：16 处调用点抛出字节级完全相同的错误串，没有判别码，生产环境无法定位根因。错误信息也是上下文，如果两条不同的故障产生同一句话，那么这句话的信息量就是零。

第四种是删除失败，表现是历史不可达。Claude Code 的 #96718 报告 Artifact 的“版本历史”菜单被移除，已经保存的版本无法再访问，影响 Claude Code、Cowork 与 claude.ai 全线产品，10 条评论、16 个赞，是当天热度最高的回归问题。同一天还有一件事：约 20 条 9 月的旧 issue 因 stale 被批量关闭，其中包含 Cowork 挂起、MCP 协议版本不匹配、credentials.json 无限增长、后台任务孤儿进程等有复现的实质性问题。

这两件事放在一起看有点刺：一边是用户保存的历史版本变得不可达，一边是项目自己的问题历史被批量标记为结束。它们和上下文压缩不是同一件事，但共享同一个前提——没有被保留的历史，等于没有发生过。

删除的极端形态在前一天的 HN 上。一条 40 分、61 条评论的帖子记录了一次真实事故：用户让 agent 帮忙给页面重新编号，结果 agent 删掉了法学院教授的整份教学大纲和一年的讲义。agent 自己的说法是“我因为自己的粗心删掉了你的文件”。这条讨论几乎没有人替 agent 辩护，社区共识集中在权限边界与沙箱化。但还有一个更朴素的角度：如果那份讲义有版本历史，这次事故的后果就只是回滚一次。删除之所以可怕，是因为它同时消灭了“内容”和“可以恢复内容的那份记录”。

第四种失败形态最容易被低估，因为它不改变任何正在运行的东西。它只是让某一类问题在下次出现时，无法被追溯。

与四种失败对应的，是三个必须做的取舍。

取舍一：摘要保真度与输出预算。摘要越长越保真，但摘要本身要花 token，而且要占输出预算。Qwen Code 的选择是给一个下限——至少 4096 个输出 token 留给摘要，做不到就降级或拒绝。OpenClaw 的选择是把上限做成可配置项，并在 release note 里明确提示：升级后如果依赖旧的完整 hydration 行为，需要检查配置。这两个选择的共同点是，它们都把“压多少”从一个隐含常量变成了显式参数。

取舍二：索引与全量扫描。全量扫描的代码最简单，代价随会话长度线性增长，最终变成 19 到 25 秒。索引快，但索引本身要维护、要占内存、会有容量上限，触顶之后还会不重试。Gemini CLI 的 #22745 提供了第三种思路：用 AST 感知的文件读取、搜索与代码库映射，只取需要的那一段语法结构，而不是把整个文件塞进窗口。这条路的前提是代码本身有结构可依；对自然语言对话，结构就得靠 transcript 索引来造。

取舍三：阻塞与后台。压缩如果同步执行，就会卡住当前轮次；如果放后台，就要处理“压缩期间新消息到达”的竞态。OpenClaw 的 #199840 修的是手动压缩期间重复拷贝 transcript 的主线程开销，Hermes Agent 一侧的 #99524、#117886、#20372 三个条目指向同一个方向：把压缩挪到后台且非阻塞。这个取舍没有免费选项，只有把代价放在哪一侧的问题。

三种取舍合起来解释了一个现象：为什么同一个问题会在七个项目里同时出现。因为这里没有统一的正确写法，只有一组没有标准答案的权衡，每个团队都在自己的负载下重新选一遍。
## 另外四个现场：状态、摘要、预算、真相

同一套记账方式，在 11 月 16 日的其他报告里还能看到四次，每一次都不涉及模型能力，只涉及“什么东西被当成了真相”。

第一次是缓存与真相的边界。Codex 的 #54538 报告：空的项目缓存导致本地数据库里完好的项目“消失”，恢复缓存之后项目又回来了。这条报告的措辞很克制，但含义不轻——当缓存成为读取路径上的唯一入口，缓存为空就等于数据不存在。上下文压缩也有同一个风险：当摘要成为恢复会话的唯一材料，摘要里没有的东西，就等于没发生过。

第二次是瞬时错误被写成永久状态。Hermes Agent 的 #119070 记录了一张 Kanban 卡片因为一次限流被永久标记为 blocker_auth，reviewer 从此再也不会触发；同项目的 #139532 是网关在轮次中途重启，把会话 fencing 成 unknown，之后的消息永久排队，桌面端没有任何解锁入口。Qwen Code 的 #17383 更直接：Runtime Broker 创建超时后会话永久卡死，状态名叫 RECOVERY_BLOCKED，字面意思就是“恢复被阻止”，且没有用户可走的路。

这三条和 #27731 是同一种病：一个瞬时事件被固化成永久状态，而系统里没有任何一处负责把它改回来。压缩造成的时态错乱正是这个病的一种——某段话在压缩那一刻是历史，之后再也没有人重新标注它。

第三次是摘要变成唯一可见物。Claude Code 的 #94032 报告 summarizedThinking 这个特性开关被强制开启，桌面端与移动端对所有模型启用思维链摘要，用户没有退出选项。这里的问题不在于摘要本身，而在于“完整版本是否还拿得到”。anthropics/skills 的 #1329 提出 compact-memory 技能，方向是给 agent 做记忆压缩；#1385 提出推理质量门禁。两件事合起来说明一件事：压缩已经不再是一个可选优化，它正在变成默认视图，于是“压缩产物的质量”变成了唯一的质量。

第四次是预算变成常量。Copilot CLI 的 #5464 说 MCP 服务器的 discover 超时只有 10 秒，慢启动的服务器直接失败；OpenClaw 的 #161158 说 gateway restart 实际上成功了却报失败，退出码还是 0，而 60 秒的就绪预算写死在代码里。这些常量单独看都很合理，合起来就是一套隐形的判定标准：谁在 10 秒内没出现，谁就被判死；谁在 60 秒内没就绪，谁就被判失败。上下文预算也是同一类东西——摘要留多少、压缩什么时候触发、快照读等多久，每一个数字都在替人做判决。

还有一条关于浪费的：#5459 说 Copilot 的后台任务用 sleep 轮询，白烧模型轮次。轮次是钱的计量单位，也是注意力的计量单位；一个 sleep 循环浪费的不只是 token，还有本可以用在别处的上下文空间。

这四个现场串起来，是一条比“压缩”更宽的线：一个系统里，被当成真相的那一层，决定了故障的形态。缓存被当成真相，清空缓存就是数据消失；状态字段被当成真相，一次限流就是永久封禁；摘要被当成真相，压缩就是失忆；常量被当成真相，慢一点就是失败。
## 准入与协议：把整块能力切成能被声明的增量

把视线上移一层，会发现“只传选中的那一块”并不只是 hydration 的技术选择，它是这一天里多个层面的共同答案。

上游的一次动作可以作对照。OpenAI 在 11 月 16 日集中发布了四十多条安全主题内容，去重后约二十四篇；日报同时记录了一个限制，全部条目的正文提取失败，分析只能基于标题与 URL 结构，这一点先记在这里。在这个前提下，标题层面呈现的动作仍然清楚：GPT-6 Cyber 是按领域切分的前沿模型，配套的 Trusted Access for Cyber 描述的是准入框架——危险能力只交给经过审查的团队；Codex Security 进入研究预览，并专门配了一篇解释“为什么不包含 SAST”的文章。准入审查就是模型层的 payload 选择器：能力不再整份发放，而是按“谁、用来做什么”切片发放。而那篇“为什么不做 SAST”的说明是另一种自觉——把边界写在功能旁边，边界可校验，比多列十项能力更能建立信任。

开源侧的同一动作出现在 GitHub Trending 上。11 月 16 日的榜单里，AgentOps 类项目第一次集中出现：NVIDIA 的 SkillEvaluator 做技能评测，包含质量门禁、语义重叠检测和合成评测集；腾讯的 LoopForge 做编码 Agent 的交付编排，带人工审批门禁；阿里的 open-code-review 用确定性规则管线加 LLM Agent 做行级评论。三者合起来是规划、执行、评审、评测的一条链，共同点是都不信任单次生成的结果。SkillEvaluator 的分量在于它回应了一个新问题：技能包爆发之后，“这个技能好不好用、和别的技能是否语义重叠”无法靠人肉阅读解决，只能靠评测集。另一侧是 Google Chrome 团队的 modern-web-guidance-src 当日新增 1220 星、chrome-devtools-mcp 新增 718 星——给编码 Agent 持续注入最新规范与真实浏览器能力，用外部增量知识源解决“模型知识过时”。

协议的层面也在同步。Copilot CLI 这一天的新旧活跃 issue 里，接近三分之一与 ACP 相关：#4275 要求 ACP 暴露 contextTier 会话配置项（8 条评论、5 个赞），理由是外部客户端需要动态调整上下文窗口；#5354 指出 ACP 不通告 Copilot Fusion 及其 tier 配置（6 个赞），于是 T3 Code 这类客户端看不到它。OpenCode 的 #54371 是反方向：ACP 下 slash 命令能执行，但输出从不流式返回，已复现，影响 JetBrains 里的使用。Qwen Code 则在把 1.0 的事件驱动内核逐个 surface 切换，headless 会话（#17336）与 Ink TUI（#17362）已经默认跑在共享 agent loop 上。

这三件事指向同一个结论：当 CLI 变成被 Zed、JetBrains、手机端消费的 agent 后端时，“我能提供什么”必须变成“你能声明你需要什么”。contextTier 是客户端对上下文预算的声明，Fusion tier 是服务端对推理档位的声明，slash 命令的流式输出是双方对交互粒度的约定。协议化的本质，是把原本混在一起的一整块能力，拆成可以被单独协商的增量。

增量化的失败形态也在同一天出现，而且都是静默的。Copilot 的 #5457 报告 Fusion 的 tier 设为 high，却被静默降级为 policy standard，没有任何警告；#4773 报告 MCP 重复发现时对已加载的 namespace 报 Found 0 tools，agent 据此判定集成不可用，直接跳过工作流步骤。两条都不抛错，两条都改变结果。

这就是增量架构的代价：一旦你只请求“选中的那一块”，你就必须有能力验证拿到的是不是那一块。整块传输的时代，缺什么一眼能看出来；增量传输的时代，缺的那一块表现为“这里本来就没有”。

## 收束：四个能自己查的信号

回到一开始那个对照。一个版本在修 hydration 与摘要上限，三条 issue 在报快照读、索引容量与 worker 被杀。同一件事的两面，说明上下文工程已经进入基础设施阶段：它不再由模型能力决定，而由索引、缓存、预算、元数据这些传统工程件决定。

如果要把这一天的材料压缩成可执行的自查，有四个信号值得放进监控。

第一个是前缀稳定性。把系统提示词、工具 Schema、记忆注入段当成接口来管理，给它们定版本号，任何顺序调整、字段增删都视为破坏性变更。判据很硬：同一段对话的连续请求里，缓存写入量应该只在第一轮出现，后续轮次接近零；如果每轮都有可观的写入，说明前缀在漂移。这一条不需要读代码，看计费明细就能发现。

第二个是压缩的次数与预算。压缩次数应该是可观测的计数器，而不是只在日志里偶尔出现的动作。每次压缩是否预留了足够的摘要输出预算，压缩后是否重新注入了当前目标与“以下是历史”的边界标记，这两件事都可以写成断言。Qwen Code 给出的 4096 是个参考值：摘要预算是输出预算的一部分，不是免费的。

如果要给压缩产物定一个最小契约，三条就够：每条摘要必须带出处，说清它由哪一轮、哪个工具的输出生成；必须带时间，明确它是历史而不是当前指令；必须标明它能不能被当作指令执行。三条都能被程序检查，也都能被模型读懂。Gemini CLI 的 #22598 要求 subagent 轨迹可以通过 /chat share 查看，本质上是同一条契约在可观测性上的落地——轨迹要能被外部审查，摘要才不至于成为唯一的真相来源。

第三个是归因粒度。花费必须能按父任务、子代理、工具调用三层拆开。父 0.04 美元、子 14.14 美元这种组合，在任何只按父任务记账的系统里都是不可见的。归因做不出来，预算就只是总额告警，永远查不到具体是谁。

第四个是读取延迟与容量上限。快照读的 19 到 25 秒、索引的 864 MiB 触顶、512 MB worker 被 OOM 杀死，这三个数字属于同一类指标：它们都在描述“状态库已经开始跟不上会话长度”。这类指标的特点是恶化平缓、没有断崖，等你感觉到慢的时候，它已经慢了很久。工具数量与单轮 token 基线也该一起看——超过 128 个工具就报 400、单轮 36.6k 的基线，都是会在扩展时突然撞上的墙。

需要说清的边界有这几条。本文的所有数据来自 2026 年 11 月 15 日与 16 日的两份开源生态日报、一份 AI CLI 工具日报、一份 GitHub 趋势日报与一份官方内容追踪日报，属于单日快照；issue 的评论数、状态、合并情况都以快照时点为准，其中若干条在发文时可能已经变化。日报本身是自动汇总产物，OpenClaw 与 Hermes Agent 两个项目的 issue 与 PR 更新量都触及了采集上限，因此这些数字只能当下限看，不能当总量。Qwen Code 的 4096 token 预算、OpenClaw 的 21.3M cache-write token、Codex 的 14.14 美元与 0.04 美元，均为报告者自述或项目方自报，本文没有独立复现。OpenAI 那批安全内容的分析建立在标题与 URL 结构上，正文全部提取失败，方向判断的置信度应当打折。

还有一个事实需要放在明处：上下文压缩这个问题，过去被当成“长会话的体验优化”，现在它同时出现在成本、正确性、协议协商三个层面。把它当优化项，就会在预算里给它留一行备注；把它当基础设施，才会给它配索引、配预算、配断言、配归因。

11 月 16 日这一天，七个项目给出的答案其实是同一个：不要让任何东西以整块的形式流动。前缀要能被稳定命中，状态要能被分段读取，摘要要能被单独计价，能力要能按用途发放，工具要能按需声明。所有这些做法都有一个前提——你得能定位到那一块。

定位不到，增量就退化成全量；而全量，是这一天所有账单的来源。
